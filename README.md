# KPI Storytelling Engine

**Accenture Innovation Challenge 2026 — Round 2, Track 3 (BusinessIntelligence.ai)**

A KPI intelligence-to-action engine: it detects material KPI movements,
reconciles evidence across two independent real-world data sources,
decomposes likely causes with deterministic statistics, states its own
confidence honestly (including abstaining when evidence is genuinely
contested), and recommends a grounded next action — with an LLM used
**only** to phrase the final narrative, never to compute a number.

> **The hard constraint this project is built around:** the LLM is never
> the source of quantitative truth. See `docs/architecture.md` for exactly
> where deterministic logic, statistics, correlation/causal-inference
> checks, and the LLM each do their (separately labeled) job.

## Quick start

### One command, both sides (Docker)

```bash
docker compose up --build
```

Backend: `http://localhost:8000` · Frontend: `http://localhost:5173`

### Manual (development)

**Backend**

```bash
cd backend
python -m venv .venv
./.venv/Scripts/activate   # Windows; use `source .venv/bin/activate` on macOS/Linux
pip install -r requirements.txt
cp .env.example .env       # fill in OPENAI_API_KEY, or leave as-is to use the local Ollama fallback
python scripts/generate_sample_data.py   # only needed if data/raw/ is empty — see "Data provenance"
uvicorn app.main:app --reload --port 8000
```

**Frontend**

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`.

### Tests

```bash
cd backend
./.venv/Scripts/python.exe -m pytest -q
```

## Data provenance — important

The two real datasets this project is built for are:

1. **Superstore retail sales** —
   [kaggle.com/datasets/rohitsahoo/sales-forecasting](https://www.kaggle.com/datasets/rohitsahoo/sales-forecasting)
2. **Customer support tickets** —
   [kaggle.com/datasets/suraj520/customer-support-ticket-dataset](https://www.kaggle.com/datasets/suraj520/customer-support-ticket-dataset)

This build environment did not have a Kaggle API token configured, so
`data/raw/` currently contains **schema-accurate placeholder data**
generated by `backend/scripts/generate_sample_data.py` — the column
headers, categorical vocabularies, and value ranges are copied from the
real datasets' documented schemas, not invented. The script also
deliberately engineers a small number of specific, labeled scenarios (a
multi-driver movement, an ambiguous movement, a sparse-history emerging
sub-category, and a lagged ticket-sentiment signal) so every item in the
brief's minimum-scenario list is reproducibly present — every injection
point is commented in the script itself.

**To use the real data:** obtain a Kaggle API token
(kaggle.com → Account → Create New API Token), then:

```bash
pip install kaggle
kaggle datasets download -d rohitsahoo/sales-forecasting -p data/raw --unzip
kaggle datasets download -d suraj520/customer-support-ticket-dataset -p data/raw --unzip
rm data/raw/*_placeholder.csv
```

**No code changes are required.** `services/data/schema_normalization.py`
matches columns by fuzzy, alias-based concept matching (e.g. "Order Date",
"order_date", and "OrderDate" all resolve to the `order_date` concept), not
exact header names — this is what lets the real Kaggle files (whose exact
headers vary slightly by mirror) normalize identically to the placeholder
data. If a required concept genuinely can't be matched, ingestion fails
loudly, naming the specific missing concept, rather than silently computing
a KPI from a misidentified column.

## Architecture

```
DATA LAYER → SIGNAL LAYER (deterministic) → REASONING LAYER (deterministic) → STORY LAYER (LLM, phrasing only)
```

Full design rationale, the LMDI driver-tree method, the correlation
quasi-control causal check, and the confidence/abstention formulas are in
[`docs/architecture.md`](docs/architecture.md). The KPI semantic contract
(definitions, formulas, grain, source, cadence, owner, materiality
thresholds, drivers, access restrictions, lineage) is
[`docs/kpi_contract.yaml`](docs/kpi_contract.yaml) — also viewable live in
the UI via the "View KPI contract" button.

### Repo layout

```
/backend/app
  /api        — thin FastAPI routers (no business logic)
  /services
    /data      — ingestion, schema normalization, KPI registry, feedback log
    /signal    — anomaly detection, NLP event extraction (deterministic)
    /reasoning — driver-tree, correlation, confidence, hypothesis engine
    /story     — LLMClient, prompts, grounding check, action recommender, cache

  /core        — config, logging, access control

```

## Objective → component mapping

| Round 2 objective | Where it's implemented |
|---|---|
| Detect & prioritize material KPI movements | `services/signal/anomaly.py` (STL/trend forecast bands + business-impact materiality floor, never statistical significance alone) |
| Reconcile data/context across heterogeneous sources | `services/data/schema_normalization.py`, `services/signal/nlp_events.py` (rule-based category bridge between the two un-joined sources) |
| Identify & rank explanatory drivers | `services/reasoning/driver_tree.py` (LMDI + mix/rate decomposition), `services/reasoning/correlation.py` |
| Persona-specific, evidence-backed narratives | `services/story/prompt_templates.py` + `services/story/grounding.py` |
| Communicate uncertainty; abstain when warranted | `services/reasoning/confidence.py` (real abstention gate over computed scores) |
| Recommend actions grounded in levers/constraints | `services/story/action_recommender.py` (static playbook; LLM only phrases the summary) |
| Learn from feedback | `services/data/feedback_store.py` + `POST /api/feedback` |
| Cost/latency/security/scale constraints | `services/story/cache.py`, `services/story/telemetry_log.py`, `core/access_control.py`, and the tiering rule in `services/story/narrative_service.py` |

## Cost, latency & scaling

- **Every LLM call is instrumented**: tokens in/out, latency, model,
  estimated cost, cache hit/miss, and tier — surfaced live in the
  Telemetry panel (`GET /api/telemetry`).
- **Caching**: `services/story/cache.py` keys on
  `(kpi_id, period, evidence content hash, persona)`. Re-requesting the
  same insight (same evidence) costs zero additional LLM calls.
- **Tiering**: `narrative_service.decide_tier` reserves the strong model
  for abstained/low-confidence insights and uses the cheap model for
  high-confidence, routine ones — the decision is read directly from the
  Reasoning layer's own confidence score, not a separate heuristic.
- **Provider**: `OPENAI_API_KEY` unset → automatic fallback to a local
  Ollama model (no cost, no external call, but CPU-bound — 30-90s per
  narrative on typical dev hardware). Configure the key for production-
  realistic latency (1-5s with `gpt-4o-mini`/`gpt-4o`).

**Scaling to "tens of thousands of interactions per week"**: at ~1,500/day
peak, with caching absorbing repeat-question traffic (the same KPI/period
is asked about far more than once) and the tiering rule keeping the
majority of calls on the cheap model, this is comfortably within a single
FastAPI instance plus a shared Redis cache (replacing the in-memory
`NarrativeCache`/`TelemetryLog` singletons — the only change needed, since
both already have a narrow get/set interface). The deterministic
Signal/Reasoning layers are pure pandas/NumPy and scale by adding workers,
not by LLM spend.

## Security & access control

- **Row-level**: a scoped persona (`leader_west`, `leader_east`) requesting
  a region outside their scope gets an explicit `403`, not a silently
  narrowed result — see `core/access_control.py` and
  `api/insights.py::_enforce_region_access`.
- **Column-level**: `GET /api/insights/{scenario}/sample-records` (the
  Evidence Viewer's raw-record drill-down) drops `customer_id`/
  `customer_name` from the response body entirely for a regional-leader
  persona — enforced server-side, before serialization.
- **Persona resolution**: this demo resolves the persona from an
  `X-Persona-Id` header (no real auth backend) — a production deployment
  would resolve it from an SSO/IdP claim instead; `get_persona()` is the
  single interface that would need to change.
- **Secrets**: `OPENAI_API_KEY` lives only in `backend/.env` (gitignored);
  `.env.example` documents every variable with no real values.

## Testing

`backend/tests/` has real, hand-verified assertions on every deterministic
function — this is the part of the system that must be provably correct:

- `test_anomaly.py` — synthetic edge cases (flat series, a sharp break,
  statistically-unusual-but-not-material, insufficient history, and a
  regression test for a real self-leakage bug caught during development).
- `test_driver_tree.py` — LMDI decomposition checked against hand-computed
  examples (isolated quantity effect, isolated price effect, zero-residual
  identity), plus the margin mix/rate decomposition.
- `test_confidence.py` — the abstention gate's every branch.
- `test_correlation.py` — the causal-vs-correlated classifier, including
  the quasi-control-group logic.
- `test_schema_normalization.py` — fuzzy column matching across header-
  naming variants, and the specific-error-on-missing-concept behavior.
